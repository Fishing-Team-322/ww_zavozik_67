# Живая проверка обязательств в учебной 1С

Срез 24.10.2026. Чтение счёта, частичной оплаты и отмены: **LIVE_VERIFIED** на отдельной учебной базе. Срок оплаты, перенос срока и счёт поставщика: **BLOCKED** фактическими данными/конфигурацией. Моковый перенос не считается живым.

## Изоляция

- Исходная файловая база: `%USERPROFILE%\Documents\1C\AccountingDemoTest`; её действующая IIS-копия: `C:\ProgramData\Codex1C\AccountingDemoTest`, адрес `/codexaccounting`.
- Клон для изменений: `%USERPROFILE%\Documents\1C\AccountingObligationsE2E`. Сразу после копирования SHA-256 `1Cv8.1CD` совпадал с исходной базой: `146A1434E39E1774D0DC3182F962ACBC790331FF892A2244E8B2117453CC8014`.
- В клоне обработка `enable-obligations-odata.epf` добавила 9 объектов к составу стандартного OData (`odata-setup.result`: `enabled=9`). Отдельная веб-копия `C:\ProgramData\Codex1C\AccountingObligationsE2E` опубликована на `http://127.0.0.1:8093/codexobligations/odata/standard.odata/`. `$metadata` вернул HTTP 200 и 33 `EntitySet`; исходный `/codexaccounting` остался отдельным.
- Восстановление: не использовать `/codexobligations`; исходная база и её публикация не заменялись. Локальные настройки и ID тестовых документов лежат вне Git в каталоге клона.

## Полученные данные

`Document_СчетНаОплатуПокупателю` вернул шесть существующих документов и созданный в клоне седьмой. `Document_СчетНаОплатуПоставщика` доступен, но существующих документов не содержит. `Catalog_ДоговорыКонтрагентов` содержит четыре договора; у всех `УстановленСрокОплаты=false`, `СрокОплаты=0`. В схеме счетов нет отдельного подтверждённого срока оплаты. Поэтому `DueDate=null`, `status=undated`, `forecast_eligible=false`; придумывать дату из даты документа нельзя.

В клон создан и проведён счёт покупателю 350 000 ₽. OData подтвердил `Posted=true`, `DeletionMark=false`, сумму 350 000 и одну строку товаров. Затем создано и проведено поступление 100 000 ₽; его строка `РасшифровкаПлатежа` содержит явный `СчетНаОплату_Key` на тестовый счёт. Адаптер прочитал семь счетов: у тестового `total_kopecks=35000000`, `paid_kopecks=10000000`, `remaining_kopecks=25000000`, `payment_status=partially_paid`, `link_status=reconciled`. Другие шесть счетов: четыре оплачены, один переплачен и требует сверки, один неоплачен на 25 000 ₽ без срока. Фактов в копии после нового поступления — 15.

Для локального воспроизведения: `go run ./cmd/verify-onec-plans --config %USERPROFILE%\Documents\1C\AccountingObligationsE2E\live-obligations-plan.json` в `integrations/`. CLI выводит только агрегаты. Сквозной тест в backend использует `TEST_DATABASE_URL` и `LIVE_ONEC_CONFIG` (файл вне Git); см. `ONEC_BACKEND_E2E.md`. Учебная 1С иногда возвращает HTTP 400 «Достигнуто предельное количество подключений к ИБ» после серии запросов; повтор после освобождения сеансов проходит. Это ограничение тестовой среды, не подтверждение стабильности промышленного подключения.

После повторной синхронизации тест снял счёт с проведения и поставил `DeletionMark=true` через живой OData. Следующая синхронизация обновила **тот же** `planned_events.id`: `payment_status=cancelled`, `remaining_kopecks=0`, `paid_kopecks=10000000`, `version=2`, `forecast_eligible=false`; таблица `onec_plan_versions` содержит две версии. Это подтвердил opt-in `TestLiveOneCBackendFacts` с `LIVE_ONEC_CANCEL=1`. На этой копии тестовый счёт теперь помечен на удаление. Для JSON PATCH стандартного OData 1С требуется `?$format=json`; без него сервер пытался читать JSON как XML и отвечал HTTP 500.

Перенос срока на живой базе не проверен: срок отсутствует и в опубликованном счёте, и в используемых договорах. Сценарий поставщика остаётся моковым, пока в копии не появится реальный исходящий счёт с документарно связанной оплатой.
