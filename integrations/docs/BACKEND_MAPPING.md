# Будущий адаптер к backend

На этом этапе backend не меняется. Самостоятельный модуль отдаёт JSON и не импортирует пакет `backend/internal/...` (правила Go для `internal` не позволяют импортировать его из соседнего модуля).

Будущий адаптер внутри `backend/internal/sources/onecbank` сможет реализовать `sources.Parser`: `Kind() -> domain.SrcOneCBankFile`, `Detect()` по маркеру `1CClientBankExchange`, `Parse()` вызовет локальный сервис или разделяемый пакет после согласования границ модулей. Текущий `sources.Parser.Parse(ctx, companyID, reader)` не принимает счёт и ИНН компании. Адаптеру потребуется получать их из записи компании/конфигурации источника либо контракт интерфейса нужно расширить по согласованию с владельцем backend. Передача только `companyID` не позволяет безопасно определить направление.

Маппинг `ImportBatch.Operations` в `sources.Batch.Operations`:

| Внешний контракт | backend |
|---|---|
| `company_id` | `domain.Operation.CompanyID` |
| `dedup_key` | `DedupHash`; `ID` присвоит слой ingest/store |
| `date` | `Date` — полночь UTC |
| `amount_kopecks` | `Amount` в рублях, только после явного преобразования и проверки точности |
| `direction` | `domain.In` / `domain.Out` |
| `counterparty_inn`, `counterparty_name`, `purpose` | `domain.INN`, `domain.Name`, `domain.Purpose` |
| `source_kind` | `domain.SrcOneCBankFile` для файла; для OData нужен отдельный вид источника в backend |
| `balance_eod_kopecks` | `BalanceEOD`, если присутствует |
| `executed=false` | не передавать в `domain.Operation` |
| `planned_events=[]` | `sources.Batch.Planned=[]domain.PlannedEvent{}` |

`domain.Operation` не содержит поля счёта и признака исполнения: счёт останется в конфигурации источника/метаданных ingest, в `Operation` попадут только подтверждённые факты. Категория и метод категоризации назначаются downstream, парсер их не угадывает. `domain.PlannedEvent` не создаётся из неподтверждённых банковских документов.

Существенное расхождение: `domain.Money` сейчас — `float64` рублей, тогда как модуль хранит `int64` копеек. `float64` не даёт гарантии точного представления десятичных копеек. На границе с backend нужен явно согласованный способ округления/проверки и тесты; предпочтительно перевести внутреннее денежное представление backend в целочисленные копейки или decimal до production интеграции. Не делать вычисления в `float64` внутри парсера.

Адаптер `onecodata` в этом модуле читает настроенные коллекции из OData по HTTPS, маппит поля и счета, использует Basic Auth и возвращает `ImportBatch`. Финансовый маппинг проверен на mock HTTP сервере. Сетевой путь и чтение записи проверены на установленной учебной 1С: товар был прочитан и отвергнут как не банковский факт. `cmd/inspect-onec` получает реальные коллекции и поля через OData. Для интеграции с приложением ещё нужны: реализация `sources.Puller` в backend, запись операций в постоянное хранилище, модель подключения компании, хранение секретов, пользовательская авторизация и фоновая синхронизация. Текущие маршруты источников в backend отвечают 501. Пока этих частей нет, подключение 1С самим пользователем через продукт недоступно.

Адаптер `dadata` предназначен для обогащения контрагента по ИНН, а не для импорта операций. Его ответ следует маппить в справочник контрагентов backend с указанием источника и времени обновления. Живой вызов требует отдельного API-ключа DaData.
