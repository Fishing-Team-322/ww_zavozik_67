# Маппинг обязательств 1С

`onecodata.PlanConfig` задаёт опубликованные наборы и поля. В отдельной публикации учебной бухгалтерии `$metadata` и HTTP 200 подтвердили `Document_СчетНаОплатуПокупателю`, `Document_СчетНаОплатуПоставщика`, строки банковских платежей, `Catalog_ДоговорыКонтрагентов` и `Catalog_Валюты`. Файл фактического маппинга `live-obligations-plan.json` хранится вне Git в каталоге клона.

| Нормализованное поле | Правило |
|---|---|
| `ExternalID` | `EntitySet:Ref_Key`; в backend ключ дополняется компанией, источником и направлением |
| `Direction` | Счёт покупателю — `in`, счёт поставщика — `out` относительно нашей компании |
| `TotalKopecks` | `СуммаДокумента` разбирается десятичным парсером в целые копейки; валюта `ВалютаДокумента_Key` проверяется по `Catalog_Валюты`, только RUB |
| `PaidKopecks` | Сумма только проведённых и подтверждённых строк банка с явным `СчетНаОплату_Key`, с проверкой организации родителя |
| `RemainingKopecks` | `max(total-paid, 0)`; переплата маркируется `needs_reconciliation` |
| `DueDate` | Только из проверенного поля срока конкретного документа. Без него `null`, `date_quality=unknown`, прогноз не получает точечное событие |
| `Status` | Отмена, полная/частичная оплата, просрочка или ожидание по проверенным полям и связям |
| `SourceVersion` | Опубликованное `DataVersion`; backend дополнительно сравнивает нормализованное содержимое и ведёт версию плана |

В опубликованном счёте не найден подтверждённый реквизит срока. Все четыре договора клона имеют `УстановленСрокОплаты=false`, `СрокОплаты=0`. Автоматически складывать срок договора с датой счёта нельзя без проверки бизнес-правила типовой конфигурации. Поэтому живой счёт 350 000 ₽ с оплатой 100 000 ₽ даёт остаток 250 000 ₽ со статусом `undated`, но не попадает в точечный 30-дневный прогноз.

`Client.FetchPlans` читает ограниченный полный снимок и возвращает его лишь после успешного чтения всех страниц. Отсутствующая строка при ошибке/частичном чтении не означает отмену. Для каждого счёта backend хранит одно актуальное событие и версии в `onec_plan_versions`; факт из 1С хранится отдельно в `operations`. Совпадение суммы/даты с банковской выпиской не доказывает связь двух фактов и не используется для их объединения. Непривязанные оплаты и счета требуют сверки.

Backend включает в прогноз только план с `data_mode=live`, известной датой, подтверждённой связью и положительным остатком; моки помечены `mock` и не попадают в прогноз. `PlannedEvent.amount_kopecks` передаёт остаток, `total_kopecks` и `paid_kopecks` сохраняются отдельно. Внешний API по совместимости всё ещё отдаёт `amount` в рублях как число, а точные копейки доступны отдельными целыми полями.
