# ТЗ: классификатор операций v2 (энкодер с несколькими выходами)

Исполнитель работает в этом репозитории, ветка `ml`. Прочитать сначала:
`docs/ARCHITECTURE.md`, `ml/README.md`, `ml/reports/classifier.md`,
`ml/models/README.md`, код текущего классификатора `ml/zavozik_ml/classify/`.

## 1. Зачем

Текущий классификатор `linear-v1` (`ml/models/classifiers/linear-v1-dac291770bf320c9`)
даёт одну категорию из 20. Для продукта и для будущего трансформера прогноза
нужно больше:

- **трансформер прогноза** (отдельная модель, делается позже) получает на вход
  не номер категории, а смысл операции: эмбеддинг и распределение вероятностей;
- **сайт** фильтрует операции не только по категории, но и по способу оплаты
  («только наличные») и по признакам («только регулярные»);
- **категории должны расширяться** без переобучения трансформера: новая
  категория появляется через обнаружение «нового явления» и подтверждение
  человеком, а не автоматически.

Классификатор и трансформер — **разные модели**. Этот документ только про
классификатор.

## 2. Что модель выдаёт на каждую операцию

| Выход | Тип | Описание |
|---|---|---|
| `embedding` | вектор float32, размер фиксирован (например 256 или 312) | смысл операции; основной вход трансформера |
| `category` | строка | самая вероятная категория (для отчётов и сумм — ровно одна) |
| `category_probs` | словарь категория → вероятность | распределение по всем категориям текущей версии справочника |
| `channel` | строка | способ оплаты, ровно один (см. справочник) |
| `channel_probs` | словарь | распределение по каналам |
| `tags` | список строк | признаки операции, ноль или несколько |
| `tag_probs` | словарь тег → вероятность | независимые вероятности по каждому тегу |
| `attributes` | объект | свойства категории для прогноза: `flow` (business / owner), `direction` (in / out / both), `mandatory` (bool), `regular_hint` (bool) |
| `novelty` | float 0–1 | насколько операция не похожа ни на одну категорию |
| `is_novel` | bool | `novelty` выше откалиброванного порога |
| `taxonomy_version` | строка | версия справочника, по которой дан ответ |
| `model_version` | строка | версия модели |

**Важно:** категория у операции одна. Несколько значений одновременно — только
у тегов. Способ оплаты — отдельная ось, а не категория: «оплата поставщику
наличными» = категория `supplier`, канал `cash`. Иначе в отчётах «расходы по
категориям» одна операция посчитается дважды.

## 3. Справочник (taxonomy)

Создать файл справочника, например `ml/zavozik_ml/classify_v2/taxonomy.json`,
с версией (`taxonomy_version`). Справочник — единственный источник правды о
классах; код не хардкодит список.

**Категории** — текущие 20 из `domain.AllCategories` (`backend/internal/domain/domain.go`).
Для каждой: `key`, `title_ru`, `description_ru` (2–4 предложения с типичными
формулировками — из него строится начальный прототип), `attributes`:

| Категория | flow | direction | mandatory |
|---|---|---|---|
| revenue_acquiring, revenue_sbp, revenue_cash, revenue_b2b, revenue_marketplace | business | in | false |
| supplier, marketing, services, utilities | business | out | false |
| salary, tax, rent, loan_payment, leasing | business | out | true |
| bank_fee | business | out | true |
| own_transfer, owner_loan | owner | both | false |
| refund | business | both | false |
| enforcement | business | out | true |
| other | business | both | false |

(`regular_hint` заполнить по смыслу: зарплата, налоги, аренда, кредиты, лизинг,
связь — true.)

**Каналы** (ровно один на операцию): `bank_transfer` (безнал по реквизитам),
`card_acquiring`, `sbp` (включая QR), `cash` (взнос/снятие наличных,
инкассация), `digital_ruble`, `marketplace_payout`, `internal_bank`
(комиссии, проценты, списания банка), `unknown`.

**Теги** (сколько угодно): `prepayment`, `partial_payment`, `final_payment`,
`budget_payment` (налоги, взносы, штрафы в бюджет), `owner_money`
(свои средства, займы учредителя), `refund`, `recurring_like`
(формулировка регулярного платежа: «за октябрь», «ежемесячная», «аванс по
зарплате»), `with_document` (есть номер и дата счёта/УПД/договора),
`enforcement` (исполнительный лист, инкассовое поручение).

Цифровой рубль — **это канал, а не категория и не крипта**. Классификация
категории — по экономическому смыслу: «оплата поставщику цифровыми рублями» →
`supplier` + `digital_ruble`; «зарплата на кошелёк цифрового рубля» →
`salary` + `digital_ruble`; «перевод собственных средств на счёт цифрового
рубля» → `own_transfer` + `digital_ruble`.

## 4. Данные и метки

- Источник: `cashflow_dataset_participants/all_operations.csv` (в git нет, лежит
  локально; UTF-8 с BOM, `;`, ИНН строкой).
- **Категории:** слабые метки — правила Go (`backend/cmd/rulelabel`, выгрузка
  `ml/data/rule_labels.csv`) и ручная доразметка из
  `ml/zavozik_ml/classify/labels.py`, как в `linear-v1`.
- **Каналы и теги:** в данных их нет. Написать разметчик по тексту назначения
  и контрагента (регулярные выражения + словари: «эквайринг», «СБП», «QR»,
  «взнос наличных», «инкассир», «цифров… рубл», «ЦР», «Wildberries/Ozon»,
  «предоплата», «частичная», «доплата/окончательный расчёт», «Казначейство»,
  «за <месяц>», «№ … от …»). Покрыть тестами. Неуверенные случаи → `unknown`
  / без тега, а не угадывание.
- **Аугментация:** переиспользовать `ml/zavozik_ml/classify/augment.py`
  (опечатки, сокращения, латиница, новые каналы, пустое назначение, без
  контрагента).
- **Разбиение строго по компаниям**, то же, что у `linear-v1`, чтобы сравнение
  было честным: списки `calibration_companies` и `test_companies` в
  `ml/artifacts/classifier/meta.json` (по 30 компаний), остальные — обучение.
  Тестовые компании не участвуют ни в обучении, ни в подборе параметров.
- **«Новые формулировки»:** `ml/zavozik_ml/classify/novel_test.csv` (280
  примеров, колонка `group` — тип случая, в том числе `digital_ruble`). Он уже
  изучался, это регрессионная проверка, а не внешний тест. Добавить свой
  отложенный набор ≥ 150 новых примеров (новые каналы, перефразировки,
  опечатки, пустое назначение) с эталоном для категории, канала и тегов —
  составить до обучения и не менять после.

## 5. Модель

- **Энкодер:** компактная русскоязычная предобученная модель текста:
  `cointegrated/rubert-tiny2` (основной вариант, быстрый на CPU) или
  `intfloat/multilingual-e5-small`. Выбор — по качеству на калибровочных
  компаниях.
- **Вход — одна строка:** направление, тип контрагента (организация / ИП-физлицо
  / пусто), название контрагента, назначение, грубый бакет суммы. ИНН не
  подавать. Нормализация — как в `ml/zavozik_ml/classify/text.py` (без удаления
  упоминания цифрового рубля: теперь это сигнал для канала).
- **Головы поверх эмбеддинга:**
  - категория — **через прототипы**: у каждой категории обучаемый вектор
    (инициализация — эмбеддинг `description_ru`), логиты = косинусное сходство ×
    обучаемая температура. Новая категория = новый прототип без переобучения
    энкодера;
  - канал — softmax-голова;
  - теги — sigmoid-голова, по выходу на тег;
  - attributes берутся из справочника по выбранной категории (не предсказываются).
- **Обучение:** кросс-энтропия по категории и каналу + бинарная по тегам;
  дополнительно supervised contrastive loss по категории, чтобы операции одной
  категории ложились рядом. Дедуплицировать почти одинаковые назначения перед
  обучением (в датасете сотни тысяч повторов одних шаблонов) и балансировать
  редкие категории.
- **Калибровка:** температура по калибровочным компаниям; порог `is_novel` —
  тоже по калибровочным.
- **Окружение:** torch и transformers уже есть в `ml/data/chronos_venv`
  (torch 2.14, transformers 5.20, MPS доступен). Прод-окружение `ml/.venv` не
  ломать: обучение — в отдельном окружении или через optional-зависимость
  `ml[train]`.
- **Инференс:** CPU, батч 256 операций ≤ 1 с на ноутбуке M1 Pro. Если torch в
  прод-образе слишком тяжёлый — экспорт в ONNX и `onnxruntime`.

## 6. Новые категории

В прод модель **сама категорий не создаёт**. Механизм:

1. Операции с `is_novel = true` копятся.
2. Офлайн-скрипт кластеризует их эмбеддинги (HDBSCAN или аналог) и выдаёт
   кандидатов: размер кластера, 10 типичных назначений, ближайшая существующая
   категория и сходство с ней, предложенные `title_ru` и `attributes`.
3. Кандидат почти совпадает с существующей категорией → это синоним, категорию
   не заводить.
4. Человек подтверждает кандидата → в справочник добавляется категория с
   прототипом = центр кластера, `taxonomy_version` растёт. Энкодер не
   переобучается.

**Проверка механизма:** спрятать одну-две категории целиком из обучения
(например `leasing`, `enforcement`), затем убедиться, что их операции на
тесте получают высокий `novelty`, кластеризуются вместе, а после добавления
прототипа из кластера классифицируются правильно. Отчитаться долей найденных и
точностью после добавления.

## 7. Критерии приёмки

На тестовых компаниях и на отложенных наборах, по сравнению с `linear-v1`:

| Метрика | Требование |
|---|---|
| Accuracy и macro-F1 категории на тестовых компаниях | не хуже `linear-v1` более чем на 0,3 п.п. |
| Accuracy категории на `novel_test.csv` | ≥ 97,9% (`linear-v1`) |
| Accuracy категории на новом отложенном наборе | лучше `linear-v1` |
| Цифровой рубль (все случаи из наборов) | категория по смыслу, канал `digital_ruble`, ни одной категории «крипта»/новой |
| Канал: accuracy на отложенном наборе | ≥ 95% |
| Теги: micro-F1 на отложенном наборе | ≥ 0,9 |
| Новизна: доля операций спрятанных категорий с `is_novel` | ≥ 80% при ≤ 5% ложных `is_novel` на известных категориях |
| Калибровка: ECE по категории | ≤ 0,05 |
| Инференс | батч 256 ≤ 1 с на CPU |

Метки датасета — от правил, не от людей: это указать в отчёте, высокие цифры
на них не называть «точностью на реальных данных».

## 8. Что сдать

1. Код: `ml/zavozik_ml/classify_v2/` — справочник, разметчик каналов и тегов,
   модель, обучение (`python -m zavozik_ml.classify_v2.train`), оценка,
   скрипт кандидатов новых категорий.
2. Модель: `ml/models/classifiers/encoder-v1-<короткий хэш>/` по правилам
   `ml/models/README.md`: веса, справочник, `README.md` (что делает, вход и
   выход, как обучена, метрики, хэши файлов, как загрузить).
3. Отчёт: `ml/reports/classifier_v2.md` — таблица против `linear-v1`, разбор
   ошибок, цифровой рубль, проверка новизны, ограничения.
4. Контракт для сервиса: новый proto `proto/categorize/v2/categorizer.proto`
   с полями из раздела 2 (v1 не трогать). gRPC-сервис v2 в
   `ml/zavozik_ml/serving/`, рядом с v1. Подключение в Go не делать — это зона
   backend.
5. Тесты (pytest): разметчик каналов и тегов, формат выхода, цифровой рубль,
   пустые и мусорные входы (модель не падает), загрузка модели из папки,
   добавление новой категории без переобучения.

## 9. Ограничения

- Не трогать прогнозную часть: `ml/zavozik_ml/forecasters/`, `ml/zavozik_ml/eval/`,
  `ml/artifacts/gbm_global/`, отчёты прогноза.
- `linear-v1` и сервис `categorize/v1` остаются рабочими — это бейзлайн и
  запасной вариант.
- Данные пользователей и датасет не отправлять во внешние API.
- Большие файлы (веса > 10 МБ, кеши, окружения) в git не коммитить; если веса
  энкодера больше — сохранить локально в `ml/models/...` и добавить путь в
  `.gitignore`, в README указать, откуда взять базовую модель.
- Коммиты — conventional (`feat(ml): ...`), в ветку `ml`, не в `main`; перед
  пушем — `git fetch` и rebase на `origin/ml`, без force-push.
- Перед пушем должны проходить `cd ml && PYTHONPATH=gen:. .venv/bin/python -m pytest -q`
  и `cd backend && go vet ./... && go test ./...`.
