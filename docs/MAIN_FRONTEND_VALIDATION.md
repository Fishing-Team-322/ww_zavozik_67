# Проверка обновлённого frontend после слияния в main

Дата: 24 октября 2026. Основа: `701c5fb` — слияние актуального frontend `44e1078` с исправлениями integration. Проверена production-сборка в локальном Docker-проекте `zavozik-full-e2e`, с настоящими API, worker, PostgreSQL и ML.

## Найдено и исправлено

- Очередь авторизации с Web Locks не проходила TypeScript-проверку и блокировала production build. Исправлена типизация асинхронного результата без отключения блокировки и сериализации.
- Отслеживание заданий обновляло refs во время React render. Стабильный refresh используется напрямую, callback обновляется в effect.
- Новая страница операций отправляла `counterparty_id=`. UUID-параметр отклонялся API с HTTP 400, поэтому операции отсутствовали в UI при корректном импорте. Неуказанные фильтры теперь исключаются из URL. Аналогично очищены фильтры документов, контрагентов, план-факта и уведомлений, в том числе необязательный boolean `unread`.
- Сохранены явное сообщение о приостановке polling и кнопка повторной проверки задания.
- E2E-сценарии адаптированы к русскому меню, календарю с диалогом события и отдельному запросу прогноза для горизонта 60 дней. Новые проверки не подменяют финансовый API.

| API / ML health | `status=ok`, `ml=ok` |

В браузере проверены:

- Вход, регистрация, восстановление пароля без токена, OAuth callback без сессии, privacy; отправка реальных писем и внешний OAuth не проверялись.
- Гость не получает данные, чужая компания недоступна, неразрешённый OData host отклоняется, ошибка источников видима, reload восстанавливает сессию.
- Изолированная учебная 1С: подключение через UI, 15 операций, 7 счетов, повторный sync с 0 новых операций и 15 дублями. Операции видны в таблице, новая операция от 24.10.2026 идёт первой. Счёт без срока не появляется в календаре. База 1С этим прогоном не изменялась.
- CSV: 240 операций с остатками; искусственный сбой первого polling-запроса и ручной повтор; обзор и прогноз 60 дней; создание платежа в новом диалоге, сохранение после reload; сохранение сценария; риск с причиной из созданного платежа.
- Дополнительные разделы с реальными ответами API: документы, регулярные платежи, план-факт, контрагенты, уведомления, настройки, методология. Проверены открытие и отсутствие ошибок загрузки; полный CRUD каждого раздела этим прогоном не покрыт.
- Финансовые экраны на ширине 375 px: обзор, операции, прогноз, календарь, сценарии и риски. Горизонтальное переполнение страницы отсутствует.
- Выход из аккаунта завершает сессию в двух вкладках; reload второй вкладки не восстанавливает вышедшего пользователя.
- Зафиксированы browser page errors и HTTP 500: в успешном прогоне отсутствуют.

## Границы результата

Это проверка локального обновлённого main. Удалённый сервер, публичный HTTPS, доставка SMTP, live DaData/Sheets/маркетплейсы и нагрузка в неё не входят. Сохраняются условия из [инструкции развёртывания](SERVER_DEPLOYMENT.md), включая настройку auth rate limit за доверенным proxy. При частых последовательных перезапусках тестов воспроизведён HTTP 429 на refresh из-за общего бюджета proxy; после завершения минутного окна итоговый прогон прошёл. Лимит не отключался и не повышался. Старый [полный отчёт](FULL_PLATFORM_E2E_REPORT.md) описывает предыдущий прогон до обновления frontend.
