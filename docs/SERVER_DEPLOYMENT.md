# Запуск на сервере

Проверенный локально вариант: Docker Compose, PostgreSQL 17, API, worker, ML и production-сборка Next.js. `compose.production.yaml` добавляет Caddy с HTTPS. Требуются Linux-сервер с Docker Compose, DNS-имя, направленное на сервер, и доступные порты 80/443. Выпуск публичного сертификата проверяется уже на сервере с этим DNS-именем.

## Настройка

Скопировать репозиторий вместе с `ml/artifacts/` и `ml/reports/metrics/`. В корне создать `.env` из `.env.example`. Задать:

```dotenv
APP_DOMAIN=finance.example.ru
PUBLIC_URL=https://finance.example.ru
FRONTEND_URL=https://finance.example.ru
COOKIE_SECURE=true
POSTGRES_PASSWORD=<случайная строка hex>
JWT_SECRET=<случайная строка минимум 32 байта>
DATA_ENCRYPTION_KEY=<32 случайных байта в base64>
SOURCE_ALLOWED_HOSTS=accounting.example.ru
```

Для генерации значений: `openssl rand -hex 32` для пароля БД и JWT, `openssl rand -base64 32` для ключа шифрования. Файл `.env` хранить с правами `600`; реальные значения в Git не добавлять. `DATA_ENCRYPTION_KEY` должен сохраняться вместе с резервными копиями БД: без него сохранённые подключения не расшифруются.

```bash
docker compose -f compose.yaml -f compose.production.yaml config --quiet
docker compose -f compose.yaml -f compose.production.yaml up -d --build
docker compose -f compose.yaml -f compose.production.yaml ps
curl --fail https://finance.example.ru/healthz
```

Миграции выполняет одноразовый `migrate` до API/worker. Данные PostgreSQL и сертификаты Caddy сохраняются в named volumes. Сервисы автоматически запускаются после рестарта Docker. Не использовать `down -v` на сервере с данными.

Открыть сайт, зарегистрировать тестового пользователя, создать компанию, загрузить тестовую выписку и проверить обзор. Для реального пользователя нужны его выписка и подтверждённый остаток: одних банковских документов OData недостаточно для расчёта остатка.

## Подключение 1С

Пользователь выбирает сетевой или файловый путь. В сетевом мастере указывает ИНН, HTTPS URL опубликованного OData и доступ чтения; discovery предлагает реальные счета организации. Администратор разрешает точный `host:port` в `SOURCE_ALLOWED_HOSTS`. Публикация должна быть доступна с сервера. Адрес `127.0.0.1` на сервере не ведёт к 1С на компьютере пользователя. Для закрытой сети нужен VPN/защищённый доступ и HTTPS; сертификат должен быть доверенным. Для private-доступа используйте явно разрешённый IP; публичное DNS-имя, разрешившееся в private/loopback/metadata IP, отклоняется. Соединение привязывается к проверенному IP при каждом dial, редиректы запрещены. Подробности для пользователя: [инструкция](INTEGRATIONS_USER_GUIDE.md).

Локальные TCP-прокси из E2E-аудита нужны только учебной 1С на Windows и не входят в production-конфигурацию. Автоматические live-тесты не направлять на рабочую базу 1С.

## Дополнительные сервисы

`DADATA_API_TOKEN`, OAuth и SMTP задаются только при наличии соответствующих учётных данных. Без SMTP доставка восстановления пароля не готова. До публичной регистрации требуется заполнить юридический документ `/privacy`.

Публичный `/v1/*` идёт из Caddy прямо в API. В `compose.production.yaml` создана сеть ingress: Caddy `172.29.245.2`, API `172.29.245.3`; API доверяет только адресу Caddy `/32`. В `X-Forwarded-For` цепочка читается справа до первого недоверенного hop. Не задавайте доверие `0.0.0.0/0` или всей сети клиентов. При конфликте подсети измените ingress subnet, оба статических IP, upstream в `infra/Caddyfile` и `TRUSTED_PROXY_CIDRS` согласованно. За внешним CDN нужна отдельная настройка доверенных прокси Caddy, не слепое доверие входящему заголовку.

Лимит ввода credentials — 30 в минуту на клиентский IP, refresh/logout — отдельные 120 в минуту. Обновления сессии больше не блокируют ввод пароля. Без доверенного proxy API игнорирует forwarding headers. В локальном варианте `localhost:3000` Next proxy несколько клиентов разделяют непосредственный адрес; это не публичная production-цепочка. Публичный путь через Caddy проверен локально: клиент A получил 30 ответов 401 и затем 429, клиент B — 401, изменяемый подложный XFF лимит не обошёл. Это функциональная, не нагрузочная приёмка.

Пользовательские источники используют `integrations/bridge` внутри API/worker. WB/Ozon подключаются через UI к backend и хранят финансовые отчёты отдельно от банка. Доступы продавца в этой приёмке отсутствуют: live не проверен. Google Sheets требует таблицу и ключ/токен чтения; OAuth flow/автопродление пока отсутствуют. Ротация ключей доступна через UI без удаления источника.

Для серверного снимка ФНС запустите Hub по `integrations/README.md`. В API/worker задайте `FNS_HUB_URL` (внутренний адрес сервиса), `FNS_HUB_TOKEN` и `FNS_HUB_COMPANY`. Не публикуйте Hub token браузеру. В Hub задайте `FNS_DEBT_INNS` и интервал `FNS_CHECK_INTERVAL` (не менее 6 часов). Текущий мониторинг ограничен операторским перечнем ИНН; автоматического расширения перечня из пользовательских workspace пока нет. API выдаёт только записи по ИНН компании и сохранённых контрагентов. Сохранённый снимок может существовать при выключенном scheduler — интерфейс показывает это отдельно. Снимок не является текущим балансом ЕНС.

`INTEGRATION_SANDBOX` в production должен быть `false`. Для тестов предусмотрен отдельный проект `puls-integration-sandbox` с `compose.sandbox.yaml`, портами 3001/8081 и собственным `pgdata`. В нём допустимы только синтетические ключи `sandbox-key` / `sandbox-client`. Не запускайте его с именем production-проекта и не подменяйте основной volume. Проверки не вводят реальные секреты в mock-стек.

Сборка с идентификатором: `GIT_SHA=$(git rev-parse HEAD) docker compose ... up -d --build`. API возвращает `X-App-Revision`, frontend — `/build-info.json`; образы имеют OCI label `org.opencontainers.image.revision`. После обновления сравните их с выбранным коммитом, затем `/healthz` и `/readyz` через публичный proxy. Выпуск настоящего HTTPS, SMTP и OAuth проверяются отдельно с реальными настройками; локальный HTTP на 8082 был только тестом Caddy.

## Обновление и сохранность

Перед обновлением сделать `pg_dump` и сохранить ключ шифрования в защищённом хранилище. Например, из корня проекта:

```bash
docker compose exec -T postgres pg_dump -U zavozik -d zavozik -Fc > zavozik-backup.dump
docker compose -f compose.yaml -f compose.production.yaml up -d --build
docker compose -f compose.yaml -f compose.production.yaml logs --tail=100 api worker frontend proxy
```

Команда запуска сохраняет volume БД. Для отката нужны предыдущий Git-коммит/образы; совместимость отката с уже применёнными миграциями проверяется отдельно. Публичное развёртывание и восстановление резервной копии на удалённом сервере в локальный аудит не входят.

Восстанавливайте backup сначала в отдельную новую БД с `createdb`, затем `pg_restore --exit-on-error --no-owner -d <restore_db> <backup.dump>`. Сравните контрольные количества, схему и доступ к данным. Не направляйте `--clean` на рабочую БД. Локальная копия до V2 восстановлена в `puls_v2_restore_20261024`: 49 пользователей, 36 компаний, 2370 операций. Рабочая БД при этом не заменялась. Backup API/Hub и ключ шифрования должны храниться вне Git и образов.
