# План: экономический смысл, открытый справочник и проверяемая иерархия

24.10.2026. Ветка `ml`. Это план следующей итерации, не отчёт об исправленном
качестве. Текущий исследовательский артефакт сохраняется неизменным.

Пользователь требует исправить смешения и сохранить автоматическое обнаружение
всего справочника/иерархии. Возврата к 20 классам, category CE по старым правилам
или ручного предопределения числа категорий не будет. В этом проходе новые fit,
экспорты, активация моделей и повторное потребление final не запускались.

## 1. Диагноз по коду и данным

1. E5-small сейчас frozen pretrained, без дообучения на экономической близости.
   Кластеризация получает общую текстовую геометрию, а не проверенную метрику
   назначения денежных потоков. Дополнительные эпохи без подходящих целей эту
   проблему не решают; у HDBSCAN нет такой настройки как эпохи обучения encoder.
2. Подготовка оставляет `сумма`/`сумма сумма`. Read-only проверка train:385
   уникальных входов direction×text превращаются в196 при удалении только
   этого placeholder.12 групп объединяют прежние разные template families,
   всего32 unique rows в этих группах. Calibration81→60 unique, новых
   пересечений семейных ID внутри этой выборки нет. Это диагностический
   эксперимент, а не уже применённая новая нормализация или новый split.
3. Источник по собственному README — **синтетические** выписки150 компаний.
   «Реальные строки» в прежнем отчёте означали исходные операции кейса вместо
   добавленной нами аугментации; это не настоящие банковские операции.
  222420 строк не означают222420 независимых экономических формулировок.
4. Один center/radius плохо описывает сложную категорию. Общие слова
   «перечисление … платы … по реестру» сблизили зарплату и земельную аренду.
   Совпадения «проведение работ» сблизили кредит и субсидию.
5. Complete-linkage строит дерево до общего предка. Выбранный по расстояниям
   coarse cut не гарантирует, что объединение экономически осмысленно.
6. Extractive title повторяет слова. Он не подтверждает содержание группы и
   способен скрыть выброс: название про зарплату не исключает аренду внутри.
7. Старый frozen test уже потреблён. Исправление известных примеров и новый
   human review тех же строк не создают новый независимый внешний тест.

Файлы диагноза: `category_discovery/{corpus,core,hierarchy}.py`,
`classify_v2/{text,splitting}.py`, corpus_v2/train_unique.jsonl,
артефакт discovery-v1-dbedf812a8a62d450b9f, README входного датасета.

## 2. Архитектура следующей версии

Операция → очистка с сохранением смысла → обученный экономический embedding →
поиск похожих операций → проверка смысловой совместимости пар → группы →
проверенные объединения в иерархии → автоматически предложенные названия.

Модель сходства отвечает на отношения, а не выбирает ID из фиксированного
справочника: «одна экономическая природа на крупном уровне», «одна подробная
группа», «разные», «недостаточно сведений». Категории/их число/имена возникают
из новых данных. Положительная coarse-пара может быть отрицательной fine-парой.

Для точных кандидатов добавить pairwise verifier (cross-encoder) и несколько
опорных операций на группу. Проверяются согласованность с представителями,
внутренние противоречия и конкурирующие группы. Один близкий центр не является
достаточным основанием. Цена дополнительного inference измеряется отдельно.

Опционально сравнить текстовую и структурированную версии представления:
«за что платят», «какая роль сторон/отношений», «какое событие описано»,
«что об этом прямо сказано». Значения открытые, каждое сопровождается
подтверждающим фрагментом/unknown. Это признаки для метрики, не скрытый каталог
20 классов. LLM не должен выдумывать отсутствующие сведения.

Неполное «окончательный расчёт» не должно превращаться в оплату зерна.
«Автомобиль» без контекста не доказывает покупку основного средства: это может
быть товар для перепродажи. Тип/отрасль бизнеса и роль контрагента исследуются
только как доступные на момент операции дополнительные признаки; запрет на
запоминание ИНН/ID и проверка переноса между компаниями сохраняются.

## 3. Порядок работ и результаты этапов

### Этап A — исправить основу до нового fit

- Отдельная версия нормализации: убрать деньги/реквизиты/НДС/остатки placeholder,
  сохраняя предмет, отрицания, роль перевода и слова, меняющие смысл.
  Канал/этап оплаты/документы хранить отдельно как признаки, чтобы они не
  становились единственным основанием категории.
- Разделить текст для сравнения дублей и текст для encoder. Предмет платежа
  не стирать из encoder ради объединения шаблонных болванок.
- Пересчитать дубли и связанные семейства; объединять все варианты исходной
  строки, аугментации и найденные near duplicates до разбиения. Одинаковое
  назначение с другим НДС/договором не считается независимой опорой.
- Новый manifest, lineage и нулевые пересечения компаний/семейств/реальных
  token inputs. Если замыкание семейств пересекает partitions — purge или
  перераспределение целой группы с отдельным отчётом потери покрытия.
- Известные смешения — открытые development regression cases. Проверять также
  настоящие положительные перефразировки, чтобы не получить «всё раздельно».

Выход: исправленный корпус и аудит; старые quality numbers не переносятся на него.

### Этап B — получить экономический обучающий сигнал

- Разметка пар на двух уровнях: same/different/uncertain для coarse и fine,
  с объяснением/источником. Категорий с заранее назначенными ID для этого не нужно.
- Начальный ориентир пилота:500–1000 разнообразных назначений и2000–3000
  проверенных пар, затем добор по ошибкам. Это ориентир объёма, не гарантия
  достаточности. Если исходных независимых примеров мало, генерирование ещё
  пар из тех же строк не заменяет новые назначения.
- Трудные отрицательные пары: зарплата/земельная аренда, кредит/субсидия,
  обслуживание долга/покупка, свои переводы/расчёты с контрагентом. Не считать
  любой близкий текст отрицательным без проверки: это создаёт false negatives.
- Положительные пары: один смысл разными словами, порядком слов, сокращениями;
  разные документы, суммы, каналы и этапы расчёта не меняют экономический объект.
- Локальная LLM может предлагать пары, свободные описания и объяснения;
  предложения и synthetic paraphrases отмечаются weak/synthetic. Согласие
  нескольких прогонов не превращается в human gold. Спорные пары разбираются,
  противоречивые must-link/cannot-link не замыкаются молча.
- Нужна независимая проверка человеком с пониманием управленческого ДДС.
  Для контроля качества разметки — два разметчика на контрольном наборе и
  разбор расхождений, включая разное понимание уровня детализации.

Выход: train-пары, отдельные validation/calibration и закрытый test с provenance.
Разбивать **операции/компании/семейства до генерации пар**. Общий endpoint пары
или его перефразировка не может находиться в разных partitions.

### Этап C — добавить данные, а не копии шаблонов

- Основной ценный добор — обезличенные назначения из дополнительных компаний,
  отраслей и независимых источников выписок, включая редкие смыслы и возвраты.
- Публичные наборы принимать только после проверки лицензии, происхождения,
  языка и того, что это действительно назначения платежей. MCC/название
  магазина/английские карточные покупки не считать эквивалентной задачей.
  Проверенный подходящий внешний корпус в этом проходе не найден и не скачан.
- Synthetic minimal pairs и локальные перефразировки полезны только для train.
  Не заполнять ими external test и не называть их банковским human gold.
- Реальные операции не отправлять внешним inference API. Локальный teacher
  генерирует только evidence-grounded предложения; encoder обучается отдельно.

Зависимость: доступ к реальным обезличенным данным и независимому эксперту пока
не подтверждён. Без них можно улучшать внутренний прототип, но нельзя доказать
«идеальное» качество на реальных выписках.

### Этап D — сравнить модели и дообучить сходство

1. После A/B сравнить frozen E5-small, multilingual-e5-base и instruction-aware
   Qwen3-Embedding-0.6B на одном закрытом validation-протоколе. Выбор кандидатов
   не является обещанием, что более крупная модель окажется лучше.
2. Два лучших по экономическим парам дообучить contrastive/triplet objective
   с проверенными hard negatives и учётом coarse/fine. Батчи не должны
   объявлять положительные пары отрицательными по умолчанию.
3. Начальный bounded recipe: до6эпох, проверка каждый epoch, patience2;
   checkpoint по validation quality. Приоритет правильного разделения
   известных экономических контрастов при сохранении положительного recall.
   Другой потолок эпох нужен только при сохраняющемся validation улучшении.
4. Финалистов проверить на3seed. Не перебирать десятки настроек по test.
   Загрузки фиксируются по revision/license/hash. Каждый fit — immutable output.
5. Для pairwise verifier сравнить небольшой дообученный cross-encoder с
   локальным instruction-model baseline. Отдельно измерить точность/цену
   verifier; retrieval relevance из готового reranker не принимать за
   экономическую совместимость без проверки.

Большая LLM может работать offline при подготовке/контроле групп. Онлайн
кандидат: компактный encoder + ограниченная проверка кандидатов. PyTorch
на сервере допустим. На16GiB M1 последовательные jobs с memory limits;
ресурсы/ETA уточняются пилотом, платные GPU/новая серверная конфигурация
заранее не подразумеваются.

### Этап E — перестроить обнаружение и иерархию

- HDBSCAN/граф близости генерирует кандидаты, pairwise semantic evidence
  проверяет их. Крупная смешанная группа разбивается, не спасается названием.
- Родитель появляется при подтверждённой coarse-совместимости дочерних групп;
  голого расстояния центров и largest-gap cut недостаточно. Проверять не только
  среднее сходство, но и конфликтующие/пограничные представители. Случайные
  пары представителей не объявлять исчерпывающим доказательством чистоты.
- Разрешить лес экономических веток. Технический общий корень in/out допустим,
  но не выдаётся за одну экономическую категорию и не разрешает ложное слияние.
- Назначать подробную группу либо только крупную группу, если уверенности в
  деталях недостаточно; иначе unknown. Согласовать thresholds на calibration.
- Новый смысл по-прежнему способен сформировать новую ветку без добавления
  класса в программный enum. Числа7/16/20 не являются целями.
- После проверки состава автоматически генерировать название/описание с
  примерами и границами. Переименование не исправляет неверное членство.

Выход: новая версия inventory/hierarchy с split/merge lineage. Не изменять
содержимое старого ID молча; миграции и старые ответы остаются воспроизводимыми.

### Этап F — измерить результат и ML-контракт

Показывать отдельно:

- coarse/fine pair precision и recall; ложные объединения и дробление;
- корректность назначенного пути по независимой проверке, отдельно для coarse
  и leaf; coverage/abstention и долю unknown, без выигрыша от отказа всем;
- разбивку по компаниям, семействам, редким смыслам и неоднозначным описаниям;
- ошибки опасных контрастов: зарплата/аренда, кредит/субсидия, собственные
  средства/операционный поток; известные случаи — regression, не внешний test;
- обнаружение целиком новых экономических явлений, исключённых из fit и
  порогов: recall при заданной частоте ложных новых групп. Поддержка scope
  определяется разметкой и несколькими непересекающимися явлениями, не old20;
- стабильность групп при новых компаниях/перефразировках, корректность версий,
  CPU p50/p95, память, cold start и одновременно несколько RPC.

Silhouette/число кластеров — вспомогательная диагностика. Текущие53.75% —
покрытие уникальных строк, их нельзя сравнивать с semantic accuracy.
Все интервалы учитывать с зависимостью строк/пар: bootstrap по независимым
компаниям/семействам или явно ограниченный вывод, не считать все пары IID.

Предлагаемые цели приёмки, которые фиксируются до нового final:

| Критерий | Целевой ориентир, не достигнутый результат |
|---|---|
| Coarse semantic precision на представительном human gold |≥99% наблюдаемая, с95% интервалом и достаточной поддержкой |
| Fine semantic precision |≥97%, отдельно от покрытия и coarse-only ответов |
| Покрытие достаточно информативных новых операций |первый ориентир≥80% хотя бы на coarse, с фиксированным определением informative |
| Известные критические контрасты |не объединяются; это regression gate |
| Название и состав |нет выявленного противоречия имени и подтверждённого состава |
| Новые явления |измеренный recall/FPR и список непроверенных областей |

Малое gold, зависимость пар, неподдержанные редкие явления или недостаточный
интервал не позволяют объявить эти цели подтверждёнными. Пороги нельзя
улучшать после просмотра final; неуспех фиксируется и требует следующего
development цикла/нового test. Гарантию100% на пустых/неоднозначных назначениях
дать невозможно — необходим корректный отказ.

Go/backend в этой задаче не менять. ML-контракт: dynamic IDs, optional coarse
или leaf, semantic evidence/score kind, версии encoder/inventory/hierarchy.
Если меняется размерность embedding — новая версия и явная downstream
миграция; не обрезать произвольный encoder-вектор до384 ради совместимости.

## 4. Контрольные точки

1. A: очистка/дедупликация/разбиение + воспроизводимый аудит и regression cases.
2. B/C: pilot-пары, инструкция двух уровней, происхождение новых данных,
   независимость gold и согласие разметчиков. До этого не обещать semantic99%.
3. D: таблица encoder/verifier экспериментов только по validation, фиксирование
   победителя и thresholds до final.
4. E/F: дерево и операции до/после, один frozen final, качество/coverage/
   latency, immutable research или accepted artifact с честным статусом.

Длительный fit, внешний download и новая автоматизация не запускаются просто
для имитации прогресса. Первый разрешённый implementation шаг — A; технически
он независим от получения новых данных и human gold.

## 5. Основания для предлагаемого подхода

- [Sentence Transformers: task-specific fine-tuning](https://www.sbert.net/docs/sentence_transformer/training_overview.html)
  — задача требует собственного определения сходства, не универсальной темы.
- [Hard-negative mining](https://www.sbert.net/docs/package_reference/util/hard_negatives.html)
  — близкие по тексту, но неверные пары полезны после проверки их меток.
- [ClusterLLM, EMNLP2023](https://aclanthology.org/2023.emnlp-main.858/)
  и [Few-shot clustering, TACL2024](https://aclanthology.org/2024.tacl-1.18/)
  — исследования роли пар/триплетов/ограничений; это мотивация эксперимента,
  не доказательство результата на банковских операциях.
- [E5-base model card](https://huggingface.co/intfloat/multilingual-e5-base)
  и [Qwen3-Embedding-0.6B model card](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)
  — кандидаты для сравнения, без заявления о превосходстве на нашем кейсе.
- [Clustering evaluation](https://scikit-learn.org/stable/modules/clustering.html#clustering-performance-evaluation)
  — геометрические метрики не заменяют эталон экономических отношений.
