# Влияние Go Hybrid на вход прогнозной модели

Реальный Go Hybrid → локальный Python gRPC, модель `classifier-v1-dac291770bf320c9`, порог 0.8. 116 development-компаний, только операции до 2026-07-01 (дата исключена), audit-компании исключены. Парсинг/дедупликация и исходные правила — те же, что в export. Ни forecast fit/audit, ни production export не изменены.

| Компаний со сменой включения операций | 82 |

Это изменение определения потока, **не экономия, не ошибка прогноза и не доказательство правильности ML-категории**. Суммы относятся ко всему выбранному периоду/набору синтетических компаний. Наблюдаемый банковский остаток не изменяется при смене категории.

Большинство новых меток уточняет `other`, но 402 перехода `other → own_transfer`, 22 `other → owner_loan` и 5 `utilities → own_transfer` меняют исключение внутренних движений. Даже переходы supplier/services/loan_payment, не меняющие общий поток, меняют признаки категорий.

Перед включением Hybrid: согласовать спорные внутренние операции по документам; зафиксировать версию политики категоризации; пересобрать отдельный development export; проверить forecast на split_v2 с причинной калибровкой и тем же upstream на обучении/сервинге. Frozen audit не использовать для выбора этой новой политики. Текущие production GBM/auto и исходный flows.csv оставлены без изменений.

Веса классификатора уже обучены на кейсе. Эта диагностика измеряет только сдвиг входа при подключении, а не обобщение на неизвестные операции. FailOpen выключен: недоступность ML завершает команду ошибкой, а не нулевым сдвигом.
