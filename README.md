# Пульс: backend финансового прогнозирования

Сервис принимает историю денежных операций малого бизнеса, строит ежедневный прогноз остатка, оценивает дату, сумму и вероятность кассового разрыва. Будущие счета, договоры, налоги и ручные планы участвуют в прогнозе; план-факт и сценарии используют те же данные.

Документ описывает текущую реализацию backend. Схемы компонентов, хранения и обработки данных находятся в [ARCHITECTURE.md](ARCHITECTURE.md).

## Возможности

- Импорт CSV, Excel и банковских файлов 1С, сопоставление полей, проверка строк, дедупликация и категоризация операций; исправления категорий пользователем.
- Обнаружение регулярных поступлений и расходов с подтверждением и редактированием. Изменённый платёж заменяет исходную оценку регулярного потока в прогнозе.
- Счета клиентов и поставщиков; договоры с явным графиком или датой начала, предоплатой и отсрочкой; частичная и полная оплата.
- Налоговый календарь, подтверждённые суммы обязательств, части НДС; загрузка кредитных графиков, зарплат и будущих поручений через собственный протокол шлюза.
- Прогноз на 7–90 дней, по умолчанию 30; квантили, риск разрыва, объяснение нехватки денег в числах и предупреждения.
- План-факт по дням/неделям, просроченные и неожиданные платежи, автоматический пересчёт после изменения данных.
- Сценарии задержки клиента, снижения выручки, внепланового расхода и роста постоянных затрат; сравнение с базовым прогнозом.
- Источники 1С OData, Google Sheets, WB/Ozon и сведения о контрагентах; доступность зависит от конфигурации и учётных данных провайдера.
- Аутентификация, компании с проверкой доступа, фоновые задания, экспорт, административные отчёты о качестве моделей.

## Подсказки по денежному потоку

На главной и в разделе «Нехватка денег» отображаются рекомендации по конкретным неоплаченным планам: согласовать перенос платежа поставщику на 14 дней, запросить оплату клиента к дате разрыва или запланировать дополнительное финансирование. Для счетов меняется ожидаемая дата оплаты; договорный срок сохраняется. Налоги, зарплата, погашение кредита и другие защищённые платежи не предлагаются к переносу.

`GET /v1/companies/{companyId}/gaps/{gapId}?horizon=30` возвращает `actions`: исходный платёж, условия, пояснение, черновик сообщения и эффект. В `effect` доступны базовая и новая нехватка (медиана и неблагоприятный вариант), уменьшение нехватки, минимальный остаток и оценка вероятности с признаком её надёжности. Эффект рассчитан на всём выбранном горизонте. Перенос за его границу помечается отдельно; проценты, комиссии и возврат финансирования не считаются известными.

`POST .../gaps/{gapId}/simulate` с `action_ids` проверяет совместный эффект без изменения плана. `POST /v1/actions/{actionId}/apply` применяет выбранное действие к плану после подтверждения в интерфейсе. Банковские операции не создаются. Устаревшие рекомендации отклоняются при изменении финансовых данных. При выписке старше семи дней или из будущего рекомендации не выдаются.

Подсказки и расчёт работают без внешней модели. Для необязательных текстовых пояснений поддержан JSON API `/chat/completions`. Пример настройки Groq в `.env` (ключ хранится только на backend):

```dotenv
CASHFLOW_LLM_BASE_URL=https://api.groq.com/openai/v1
CASHFLOW_LLM_API_KEY=<ваш ключ>
CASHFLOW_LLM_MODEL=qwen/qwen3.8-27b
```

Выберите доступную модель с JSON mode в кабинете провайдера; модель и квоты могут меняться. Перезапустите API и worker после настройки. Без этих переменных используются встроенные пояснения. Для локального Ollama укажите `http://localhost:11434/v1`, имя установленной модели и оставьте ключ пустым; этот адрес относится к локальному запуску Go-процесса. В Docker локальная модель должна быть доступна из контейнера по HTTPS либо через настроенный локальный прокси.

Во внешний API передаются только вид действия и логические признаки его рассчитанного эффекта. Названия компаний, реквизиты, документы, назначения платежей, суммы и даты не отправляются. Ответ модели не участвует в финансовых вычислениях. При таймауте, лимите или некорректном JSON остаются встроенные пояснения; черновики сообщений составляются сервисом и автоматически не отправляются.

Бесплатные варианты: [Groq — квоты Free Plan](https://console.groq.com/docs/rate-limits), [OpenRouter — бесплатные модели и ограничения](https://openrouter.ai/docs/faq), [локальный Ollama — совместимый API](https://docs.ollama.com/api/openai-compatibility). Для OpenRouter base URL — `https://openrouter.ai/api/v1`; выберите конкретную бесплатную модель с поддержкой JSON mode. Условия тарифов проверены 25 октября 2026 года; точная квота аккаунта отображается у провайдера.

## Запуск через Docker Compose

Из корня репозитория:

```powershell
Copy-Item .env.example .env
```

Заполнить в `.env`:

| Переменная | Значение |
| --- | --- |
| `POSTGRES_PASSWORD` | Новый пароль БД; для Compose-URL удобно использовать буквы и цифры |
| `JWT_SECRET` | Случайная строка, минимум 32 байта |
| `DATA_ENCRYPTION_KEY` | Base64 от 32 случайных байт; одинаковый ключ для API и worker |
| `PUBLIC_URL`, `FRONTEND_URL` | Для локального запуска оставить значения примера |
| `COOKIE_SECURE` | `false` для локального HTTP, `true` для HTTPS |

Получить случайную строку и отдельно ключ шифрования можно командами:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
python -c "import secrets,base64; print(base64.b64encode(secrets.token_bytes(32)).decode())"
```

Запустить серверную часть и существующий ML-сервис:

```powershell
docker compose up -d --build postgres migrate ml api worker
Invoke-RestMethod http://localhost:8080/healthz
docker compose logs --tail 50 api worker
```

`migrate` применяет встроенные миграции, включая `00010` и `00011`. API доступен на `127.0.0.1:8080`; worker обрабатывает очередь в PostgreSQL. Compose не запускает демонстрационный шлюз обязательств автоматически: его запуск описан ниже. Обучаемый TrxGPT подключается отдельно после подготовки serving-сервиса.

## Запуск Go-процессов локально

Нужны PostgreSQL 17 и Go с загрузкой toolchain из `backend/go.mod` (Go 1.26.10). Приложение читает переменные окружения напрямую; файл `.env` сам по себе загружается только Compose.

В каждой консоли настроить одинаковые `DATABASE_URL`, `JWT_SECRET`, `DATA_ENCRYPTION_KEY`. Для локального HTTP также задать `COOKIE_SECURE=false`, `PUBLIC_URL=http://localhost:8080`, `FRONTEND_URL=http://localhost:3000`. `ML_ADDR=localhost:50051` указывает gRPC-модель; пустое значение включает работу со встроенным резервным прогнозом Seasonal Naive.

```powershell
Set-Location backend
go run ./cmd/migrate
go run ./cmd/api
```

В другой консоли с тем же окружением:

```powershell
Set-Location backend
go run ./cmd/worker
```

## Наполнение локального стенда из датасета

Скрипт [scripts/seed-demo.py](scripts/seed-demo.py) читает ZIP кейса напрямую или каталог с `companies.csv` и `statements/`. Нужны запущенные API, worker и PostgreSQL; для полного прогноза также ML. Дополнительные Python-пакеты не требуются.

```powershell
$env:PULS_DEMO_PASSWORD = '<пароль локального демонстрационного аккаунта>'
python scripts/seed-demo.py --dataset C:\Users\beesknight\Downloads\cashflow_dataset_participants.zip --dry-run
python scripts/seed-demo.py --dataset C:\Users\beesknight\Downloads\cashflow_dataset_participants.zip
```

По умолчанию создаётся аккаунт `demo@puls.local` и три компании: грузоперевозки `C001`, клиника `C008`, кофейня `C016`. Все сущности помечены «Демо» в названиях. Скрипт передаёт операции через штатный импорт, дожидается фоновых заданий и проверяет прогноз на 30 дней. Счета, договор, отдельное налоговое обязательство, план оборудования и три сценария создаются через тот же API, который использует фронтенд. Для клиники добавляется крупный демонстрационный расход, чтобы показать риск нехватки денег. Новые обязательства синтетические и не выдаются за документы из датасета.

Даты выписок по умолчанию сдвигаются к вчерашнему дню UTC. Сдвиг и идентификаторы фиксируются в `.local/demo-seed.json`; повторный запуск с тем же состоянием добавляет ноль операций и не дублирует документы/планы. Пароль и access token в состояние не сохраняются. Не удаляйте checkpoint между обычными повторными запусками. Изменённый датасет или другой сдвиг требуют отдельного `--state`, чтобы не смешивать разные демонстрации.

Опции:

- `--list` — показать компании и отрасли без запросов к API.
- `--companies C001 C008` — выбрать компании; `--all` — импортировать все 150.
- `--history-only` — загрузить только выписки.
- `--as-of original` — оставить исходные даты; `--as-of 2026-10-24` — задать дату окончания.
- `--email`, `--api-url`, `--state` — другой локальный аккаунт, адрес и checkpoint.

Обезличенные ИНН из `companies.csv` могут не проходить официальную контрольную сумму, поэтому скрипт не задаёт их как подтверждённые реквизиты компании. ИНН контрагентов в импортируемых операциях сохраняются строками, включая ведущие нули. Суммы и фактические остатки переносятся с точностью до копейки; неизвестный остаток не превращается в ноль.

Подготовленный в этой задаче стенд работает под Compose-проектом `puls-demo`. Его конфигурация — `.local/demo.env`, данные входа — `.local/demo-access.json`. Эти файлы исключены из Git и Docker build context. Для повторного запуска:

```powershell
docker compose --project-name puls-demo --env-file .local/demo.env up -d
$env:PULS_DEMO_PASSWORD = (Get-Content .local/demo-access.json -Raw | ConvertFrom-Json).password
python scripts/seed-demo.py --dataset C:\Users\beesknight\Downloads\cashflow_dataset_participants.zip
```

Тесты скрипта: `python -m unittest discover -s scripts/tests -p 'test_*.py' -v`. При `PULS_SEED_TEST_API_URL=http://localhost:8080` дополнительно выполняется два импорта в отдельный синтетический аккаунт с проверкой неизменности операций и планов; эта проверка включена в Docker job CI.

## Собственный банк / учётный шлюз

`backend/cmd/obligations-api` — собственный демонстрационный провайдер, сохраняющий снимки обязательств в JSON-файл. Он моделирует банковский и учётный API; данные явно помечаются `data_mode=demo`.

Из каталога `backend/` задать:

```powershell
$env:OBLIGATIONS_HTTP_ADDR = '127.0.0.1:8092'
$env:OBLIGATIONS_API_TOKEN = '<случайный токен чтения, минимум 32 символа>'
$env:OBLIGATIONS_ADMIN_TOKEN = '<другой случайный токен записи, минимум 32 символа>'
$env:OBLIGATIONS_DATA_FILE = '<абсолютный путь к JSON-файлу в существующем каталоге>'
go run ./cmd/obligations-api
```

Администратор записывает полный снимок через `PUT /v1/companies/{inn}/bank/obligations` или `/tax/obligations` с `Authorization: Bearer <токен записи>`. Чтение через `GET` использует токен чтения. Формат и примеры: [контракт шлюза](api/obligations.openapi.yaml), [подробная инструкция](runbooks/BACKEND_CASE_COMPLETION.txt).

На API и worker разрешить точный `host:port` провайдера в `SOURCE_ALLOWED_HOSTS`. Для процесса на этом же компьютере это `127.0.0.1:8092`; контейнерам нужен доступный им адрес шлюза (удалённые URL требуют HTTPS). У компании должен быть соответствующий ИНН. Создать источник `bank_api` или `tax_api`:

```json
{
  "kind": "bank_api",
  "title": "Наш демонстрационный банк",
  "config": {
    "url": "http://127.0.0.1:8092/v1/companies/7707083893/bank/obligations",
    "token": "<токен чтения>"
  }
}
```

Запросы: `POST /v1/companies/{id}/sources`, затем `POST /v1/sources/{id}/test` и `/sync`. Синхронизация возвращает задание `202`; результат проверяется через `GET /v1/jobs/{id}`. Токен источника хранится зашифрованным.

## Правила финансовых данных

Суммы основного API — рубли с точностью до копейки, шлюза — целые копейки. `operations` содержит фактические движения денег. Планы и отметка об оплате документа сами по себе не создают банковскую операцию и не меняют фактический остаток.

Новые счета и договоры по умолчанию имеют `additional=true` и добавляются к модельному потоку. `additional=false` явно означает, что обязательство уже покрывается моделью. Подтверждённые регулярные платежи, найденные в истории, заменяются через поправку к исходному графику: например, аренда 1000 → 2000 уменьшает прогноз ещё на 1000. Это поправка к оценке, а не идентификация конкретной транзакции внутри модели.

Банковское поручение связывается со счётом по `related_event_id` либо номеру счёта (`document_number` или явное упоминание в назначении) и совпадающим реквизитам. Требуются одинаковые сумма, направление, дата и непротиворечивый контрагент. Неоднозначные совпадения остаются отдельными записями. Связанное поручение видно в API со статусом `linked` и ссылкой на основное обязательство; в финансовых итогах учитывается одна запись. Если оплата была сопоставлена с поручением раньше добавления счёта, она переносится на счёт один раз.

Налоговый шлюз передаёт **остаток долга**. После оплаты части НДС новый остаток распределяется только между неоплаченными частями; подтверждённая история сохраняется. Повтор одного и того же снимка не восстанавливает погашенную задолженность. Например, после оплаты 33,34 из 100,01 будущие части в сумме составляют 66,67. Исчезнувшие из полного снимка неоплаченные планы отменяются. Сервис составляет календарь из подтверждённой суммы налога, а не вычисляет налоговую базу из всех поступлений по выписке.

## Проверка тестами

Карта проверки рабочих экранов, действий и задач со звёздочкой: [аудит связки интерфейса и backend](runbooks/UI_BACKEND_AUDIT.txt). Браузерные регрессии запускаются через `npm run test:e2e` из `underfront/` против отдельного тестового стенда. Для проверки администратора нужны `E2E_ADMIN_EMAIL` и `E2E_ADMIN_PASSWORD` синтетического аккаунта с ролью admin в этой тестовой БД; CI подготавливает его самостоятельно.

Production: [suck-and-see.net](https://suck-and-see.net). После успешного CI текущего `main` workflow `deploy production` собирает образы в GitHub Actions и развёртывает их через ограниченный SSH-доступ. Конфигурация, проверки готовности, резервные копии и возврат к предыдущей версии описаны в [инструкции деплоя](deploy/OPERATIONS.txt). Серверные ключи и настройки хранятся вне репозитория.

Если соединение с Cloudflare обрывает загрузку крупных файлов, доступен [резервный HTTPS-адрес напрямую](https://puls-85-159-231-68.sslip.io). Он использует тот же backend и базу; настройки проксирования основного домена остаются прежними.

Интеграционные тесты требуют `TEST_DATABASE_URL`; без него проверки БД пропускаются. Каждый тест создаёт и удаляет собственную схему. Пример отдельной тестовой БД:

```powershell
docker run -d --name zavozik-test-pg -e POSTGRES_USER=tester -e POSTGRES_PASSWORD=local-test-password -e POSTGRES_DB=zavozik_test -p 127.0.0.1:15433:5432 postgres:17-alpine
docker exec zavozik-test-pg pg_isready -U tester -d zavozik_test
$env:TEST_DATABASE_URL = 'postgres://tester:local-test-password@127.0.0.1:15433/zavozik_test?sslmode=disable'
Set-Location backend
go test ./... -race -count=1
go vet ./...
Set-Location ../integrations
go test ./... -race -p 1 -count=1
go vet ./...
```

Для `-race` на Windows нужен C-компилятор в `PATH`. В `integrations` параметр `-p 1` запускает пакеты последовательно: их PostgreSQL-тесты создают общую схему standalone-хранилища. Живой ML и живая 1С проверяются отдельными opt-in тестами; отсутствие их конфигурации означает пропуск. Тесты провайдеров используют контролируемые серверы и синтетические данные. Unix-проверки `/dev/full` и SIGTERM пропускаются на Windows.

Регрессии трёх бизнес-ошибок находятся в [business_requirements_regressions_test.go](backend/internal/httpapi/business_requirements_regressions_test.go): влияние изменений регулярного платежа на прогноз, единый учёт счёта и поручения, остаток НДС после оплат и повторных синхронизаций.

## Модель и границы текущего прототипа

Go передаёт модели дневную историю и исходные упорядоченные операции: дату, сумму, направление, категорию, псевдоним контрагента и назначение. Самодельный трансформер может строить из них токены транзакций. Для продукта serving должен вернуть дневные пути поступлений/списаний по общему gRPC-контракту. После обучения остаётся подключить и проверить этот serving, обновив его Python bindings. Код обучения этой веткой не меняется.

Backend уже умеет повторно использовать модельные траектории с новым фактическим остатком и отдельно пересобирать планы. Это обновление продуктового прогноза, а не дообучение трансформера. Версия модели, fallback и режим обновления отражаются в ответе.

Существующие отчёты сравнения прогнозов лежат в [ml/reports/metrics/final_audit.summary.csv](ml/reports/metrics/final_audit.summary.csv); это оценка прежних подходов на синтетических компаниях, она не подтверждает качество ещё обучаемого TrxGPT. WB/Ozon поставляют отчёты; открытые сведения ФНС — контекст риска. Реальные денежные движения подтверждаются выпиской. Подробности ограничений и конфигурации приведены в [инструкции backend](runbooks/BACKEND_CASE_COMPLETION.txt).
